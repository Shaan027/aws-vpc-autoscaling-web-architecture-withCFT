What happens to a request

  1. The browser sends a request to the ALB DNS nameAn HTTP GET on port 80. The DNS name points to ALB nodes in both public subnets.
  2. The Internet Gateway lets it into the VPCThe public route table sends 0.0.0.0/0 to the IGW, so the ALB is reachable from the internet.
  3. The ALB picks a healthy server: this time, Server 2Both servers are in the target group. The ALB alternates between them and skips any target that fails its health check.
  4. The security group admits only the ALBThe private EC2 security group allows HTTP only from the ALB security group. Nobody can reach the server directly.
  5. The server returns index.html and the reply goes back the same wayYou never see the server real address, only the ALB.

Jump through the bastion with your own key file and IPs:

Why it is built this way

A normal beginner setup is one EC2 instance with a public IP. It works, until it does not. This architecture fixes the weak spots one by one.

It survives failures

Two web servers sit in two different Availability Zones, which are physically separate data centres. If one server or one whole zone dies, the other keeps answering.

It hides the servers

The web servers live in private subnets with no public IP. Attackers cannot even address them. Only the load balancer is exposed to the internet.

It has one stable address

Users only know the ALB DNS name. You can stop, replace or add servers behind it and nobody has to change anything.

It controls admin access

Nobody logs in to the web servers from the internet. Admins go through a single bastion host with key-based login, and only the bastion is allowed to SSH into the private servers.

Security: who can talk to whom

Security groups are firewalls attached to each instance. The trick is that a rule can say "allow traffic from that security group" instead of an IP address. That is how the private servers accept traffic only from the ALB.

Routing: what makes a subnet public or private

A subnet is not public or private by itself. The only difference is its route table. A subnet whose route table sends internet traffic to an Internet Gateway is public.

Public route table

DestinationTarget
VPC rangelocal
0.0.0.0/0Internet Gateway

Used by public subnets A and B. This is where the ALB and the bastion live.

Private route table

DestinationTarget
VPC rangelocal
0.0.0.0/0no route

Used by private subnets A and B. With no NAT Gateway in this design, the web servers cannot reach the internet either, in or out.

Health checks and failover

The ALB does not trust that a server is alive. It checks, over and over, by requesting the page itself. A server that stops answering is removed from rotation automatically.

NormalThe ALB requests the page from each server on a schedule. Both answer 200 OK.
Server stopsChecks begin to fail. The ALB still sends it traffic, so some users may see errors.
Marked unhealthyAfter enough failed checks the ALB stops using it. All traffic goes to the other server.
RecoveredAfter enough passing checks the server rejoins and traffic is shared again.

Interval10 secondsHow often each server is checked

A server is removed after about 20 seconds of failures and returns after about 20 seconds of passes. The lab above runs a little faster so you can watch the whole cycle.

The ALB uses round robin. What does that mean?

Request 1 goes to Server 1, request 2 to Server 2, request 3 to Server 1, and so on. It is the ALB default and it only counts healthy servers. The ALB also spreads traffic across both Availability Zones even if one has fewer servers.

Why does my browser sometimes show the same server twice?

The ALB balances each request, but your browser can cache a page or reuse a connection, so a refresh may not look like a fresh request. The real test above adds a unique value to every request to avoid that.

I stopped and started an instance. Why does it stay unhealthy?

The web server is launched by the instance user data, which runs only on the first boot. After a stop and start the instance is running but nothing listens on port 80. Log in through the bastion and run sudo sh -c 'cd /opt/website && nohup python3 -m http.server 80 >/dev/null 2>&1 &'. To test failover without stopping the instance, use sudo pkill -f http.server instead.
